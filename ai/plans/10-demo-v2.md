# แผน 10: สัญญาข้อมูล v2 + `/demo` ยืดหยุ่น 3 ระดับ + ภาพขั้นตอนอัลกอริทึม (รอบปรับปรุง v2)

**เป้าหมาย:** `/demo` รับเอกสาร TMD ได้กว้างขึ้นและแสดงให้เห็นทีละขั้นว่าไปป์ไลน์ทำอะไรกับเอกสาร โดยผลสรุปของชนิดเดิมไม่เปลี่ยนแม้แต่ไบต์เดียว

**สเปก:** [../../docs/spec/data-contract.md](../../docs/spec/data-contract.md) · [../../docs/spec/scope-and-pipeline.md](../../docs/spec/scope-and-pipeline.md) · ADR 0002 (ขอบเขตเอกสาร 2 ชนิด) · ADR 0013 (คำอธิบายเกณฑ์จาก TMD เท่านั้น) · `src/tmd_plain/service.py`, `api/summarize.py`

**ที่ผู้ใช้ตกลง (2026-11-18):**
- `/demo` 3 ระดับ: (1) ชนิดที่รู้จัก → ผลเต็มแบบเดิม (2) เอกสาร TMD อื่น → **โหมดทั่วไป**: ไม่เขียนใหม่, แสดงโครงเอกสาร, ป้ายบทบาทประโยคพร้อมความมั่นใจ (ต่ำ = "ไม่แน่ใจ"), คำแนะนำที่ดึงได้, จังหวัด→ภาค, คำอธิบายศัพท์จาก TMD เท่านั้น, ไฮไลต์ตัวเลข/วันที่, แท็บภาคถ้ามีหัวข้อภาค (3) ไม่มีชั้นข้อความ (ภาพล้วน) → ปฏิเสธแบบสุภาพ; เอกสารอื่นที่มีข้อความแต่ดูไม่ใช่ TMD → แสดงพร้อมคำเตือน
- ภาพขั้นตอน (trace) เปิดเป็นค่าเริ่มต้น มีปุ่ม "ถัดไป / ย้อนกลับ" ขั้น: อ่าน PDF, ทำความสะอาด, ตรวจชนิด, แบ่งส่วน, แบ่งหน่วย, ตัดคำ (newmm), คัดคำ (เฉพาะที่ทำจริง: ทิ้งเครื่องหมาย, ตัวเลข→`<num>`, ข้ามคำนอกคลัง; **ไม่มี** stop-word), NB จัดประเภท (คะแนน ความมั่นใจ คำเด่น), แยกตามภาค, ดึงข้อเท็จจริง (regex), เทมเพลต, ตรวจ F1-F5, ผลลัพธ์
- trace ขับด้วยข้อมูลตามชนิดเอกสาร · ผลลัพธ์เมื่อเปิดหรือไม่เปิด trace ต้องเหมือนกันทุกไบต์
- อนิเมชันในขั้นตอน: ชิปคำไหลออก, คำที่ถูกคัดจางหาย, แท่งคะแนนยืด, ชิปย้ายเข้าภาค, ข้อเท็จจริงเข้าเทมเพลต, เครื่องหมายถูกของการตรวจ (กติกาแผน 07: ไม่ทำอนิเมชันกับค่าตัวเลข, reduced-motion)

**ข้อจำกัดที่ใช้:** เปลี่ยนสัญญาข้อมูลต้องมี ADR (ห้ามเงียบ) · หลังแก้ `contract.py` รัน `scripts/export_schema.py` · ความถูกต้องของผล: ทุกตัวเลข/จังหวัด/คำแนะนำมาจากต้นฉบับคำต่อคำ, โหมดทั่วไป **ไม่เขียนข้อความใหม่** · ขีดจำกัด Vercel (body 4.5 MB, ฟังก์ชัน 300 วินาที, bundle 500 MB) · ห้ามเพิ่ม dependency โดยไม่ถาม

**เงื่อนไขเริ่ม:** 10.1 หลัง 9.1 (ต้องมีตัวอย่างจริง) · 10.4 หลัง 7.2 · ลำดับ 10.1 → 10.2 → 10.3 → 10.4

## Phase 10.1: สัญญาข้อมูล v2 + ADR   [M]   [เจ้าของ: ผู้ช่วย; ผู้ใช้อนุมัติ]

Goal: สัญญาข้อมูลที่รองรับทุกชนิดในรอบนี้ ออกแบบจากตัวอย่างจริง และผู้ใช้อนุมัติก่อนเขียนโค้ดต่อ

Inputs
- ตัวอย่างจาก 9.1 (เดินเรือ, ประกาศเตือนภัย, สรุปรายสัปดาห์, ชุด generic), `src/tmd_plain/contract.py`, `lib/contract/`, `db/` (ตาราง `forecast_issue`)

Tasks
1. อ่านตัวอย่างทุกชนิดแล้วร่างโครง (เขียนลง `docs/spec/data-contract.md` หัวข้อ v2 ก่อน ยังไม่แก้โค้ด):
   - `ShippingIssue` (ลักษณะอากาศทั่วไป + บล็อกพื้นที่ทะเล: ลม ทิศ ความเร็ว (นอต + กม./ชม. ตามต้นฉบับ), คลื่น, คำเตือนเรือ)
   - `WarningNotice` (หัวเรื่อง, ฉบับที่/เลขประกาศ, ช่วงที่มีผล, ระดับตามคำของ TMD คำต่อคำ ไม่สร้างสเกลสีเอง, จังหวัด/ภาคที่กล่าวถึง, ข้อควรระวัง)
   - `WeeklySummary` (ช่วงวันที่, สรุปลักษณะอากาศ, ตัวเลขฝน/อุณหภูมิตามตาราง)
   - `GenericDocument` (ส่วน, หน่วย + ป้าย + ความมั่นใจ, คำแนะนำ, การกล่าวถึงจังหวัด/ภาค, ศัพท์ที่อธิบายได้, ตัวเลข/วันที่)
   - `Trace` (รายการขั้น: id, ชื่อ, ข้อมูลเข้า/ออกแบบย่อ; จำกัดขนาด)
   - `SummarizeOk` แยกตาม `kind` (`issue` / `shipping` / `warning` / `weekly` / `generic`) + `trace?`
2. ข้อตัดสินใจที่ต้องถามผู้ใช้ใน phase นี้: (ก) ป้าย `cause` / `weather` จะมีบทบาทจริงในผล (เช่น แยกส่วน "สาเหตุ" ในสรุป) หรือคงไว้ใช้แค่ "คำแนะนำหรือไม่" (ข) ขนาด trace สูงสุดต่อคำขอ
3. ADR ใหม่ "data contract v2" (แก้ขอบเขต ADR 0002: จาก 2 ชนิดเป็นชนิดที่ระบุ + โหมดทั่วไป) และแผนย้าย DB: เปลี่ยน check constraint ของ `doc_type` (ยังไม่รันจริง รันใน 11.1 เมื่อผู้ใช้อนุมัติ)
4. หลังผู้ใช้อนุมัติ: แก้ `src/tmd_plain/contract.py` + `scripts/export_schema.py` → `lib/contract/*.schema.json` + Zod ใน `lib/contract/` + เทสต์สัญญา (ไฟล์ตัวอย่างต่อชนิดผ่านทั้ง pydantic และ Zod)
5. อัปเดต `.claude/CLAUDE.md` บรรทัด "Only two document types are supported" ให้ตรงกับ ADR

Checks
- pytest + `npm test` ผ่าน · schema ไม่เก่า (เทสต์เดิม) · `npm run load:neon -- --dry-run` ยังผ่าน 35 ไฟล์ (ชนิดเดิมไม่เปลี่ยน)
- `data/processed/` เท่าเดิมทุกไบต์

Human steps
- ผู้ใช้อนุมัติร่างสัญญา v2 + ADR และตอบข้อตัดสินใจ (ก) (ข) **ก่อน** task 4

Stop conditions
- ตัวอย่างจริงมีโครงต่างกันมากจนสัญญาเดียวไม่พอ → เสนอแยกหรือลดขอบเขต รอผู้ใช้

Out of scope
- ตัวแยกส่วน/ดึงข้อมูลของชนิดใหม่ (แผน 11), migration จริง (11.1)

## Phase 10.2: ทะเบียนชนิดเอกสาร + trace ในรายวัน/7 วัน   [M]   [เจ้าของ: ผู้ช่วย]

Goal: ไปป์ไลน์มีทะเบียนชนิดเอกสารศูนย์กลาง และรายวัน/7 วันส่ง trace ได้ โดยผลไม่เปลี่ยน

Inputs
- สัญญา v2 (10.1), `src/tmd_plain/prep/doctype.py`, `pipeline.py`, `service.py`, `classify/`, `extract/`, `generate/`

Tasks
1. `src/tmd_plain/doctypes/` (หรือ `registry.py`): ชนิด → ตัวตรวจจับ, ตัวแยกส่วน, ตัวสร้างผล, ขั้นของ trace · `detect_doc_type` ใช้ทะเบียนนี้ · เพิ่มชนิดใหม่ = เพิ่มรายการ ไม่แก้ `service.py`
2. ตัวเก็บ trace แบบส่งเข้าไปเป็นอาร์กิวเมนต์ (ค่าเริ่มต้น = ไม่เก็บ) ไม่มี global state; แต่ละขั้นของรายวัน/7 วันบันทึกข้อมูลย่อ (ตัวอย่างโทเคน, คำที่ถูกคัด, คะแนน NB ต่อ class + คำเด่น, ภาค, ข้อเท็จจริง, ผล F1-F5)
3. `service.summarize_pdf(..., trace=True|False)` · `api/summarize.py` รับ `?trace=1` · จำกัดขนาด trace ตามข้อ (ข) ของ 10.1
4. เทสต์: ทุกไฟล์ใน `data/processed` สร้างซ้ำได้เท่าเดิมทั้งเปิด/ปิด trace (`tests/pipeline/test_trace_identity.py`), trace ของ 1 ฉบับเป็น golden, เวลาเพิ่มจาก trace < 20% (วัดบนเครื่อง)

Checks
- `scripts/run_pipeline.py` → 35 ไฟล์เท่าเดิมทุกไบต์ · `check_fidelity.py` `errors: 0` · pytest, ruff ผ่าน
- `tests/api`: POST PDF ตัวอย่างพร้อม `?trace=1` ได้ 200 + trace ตามสัญญา; ไม่ใส่ได้ผลเดิม

Human steps
- none

Out of scope
- โหมดทั่วไป (10.3), UI (10.4)

## Phase 10.3: โหมดทั่วไปสำหรับเอกสาร TMD อื่น   [M]   [เจ้าของ: ผู้ช่วย]

Goal: PDF ของ TMD ที่ไม่ใช่ชนิดที่รู้จักได้ผลแบบ `GenericDocument` แทนการปฏิเสธ; ภาพล้วนยังปฏิเสธ

Inputs
- 10.2, ชุด `data/raw/generic/` (9.1), `resources/glossary.toml`, แผนที่จังหวัด→ภาค

Tasks
1. `src/tmd_plain/generic/`: แบ่งส่วนจากหัวข้อ (กฎ), แบ่งหน่วยเหมือนเดิม, ป้ายจาก NB เดิม + ความมั่นใจ (ใต้เกณฑ์ใน `config.toml` = "ไม่แน่ใจ"), คำแนะนำ = หน่วยที่เป็น advice คัดลอกคำต่อคำ, จังหวัด→ภาค, ศัพท์จาก glossary ของ TMD เท่านั้น, ตัวเลข/วันที่ด้วย regex, แท็บภาคถ้าพบหัวข้อภาค
2. ตรวจว่า "น่าจะเป็นเอกสาร TMD" ด้วยกฎ (ชื่อกรม, รูปแบบหัวเอกสาร) → ไม่ใช่ = ยังแสดงแต่มี `warning: "not_tmd_like"`; ไม่มีชั้นข้อความ → `extract_failed` ข้อความเดิม
3. trace ของโหมดทั่วไป (ขั้นที่ทำจริงเท่านั้น)
4. ตรวจความถูกต้องแบบ F: ทุกตัวเลข/จังหวัด/คำแนะนำในผลพบในข้อความต้นฉบับ (`check_generic` + เทสต์บนชุด generic ทุกไฟล์)
5. Golden ของ 2-3 ไฟล์ generic

Checks
- pytest (รวมเทสต์ใหม่) + ruff ผ่าน · ทุกไฟล์ใน `data/raw/generic/` ได้ผลหรือข้อผิดพลาดที่มีรหัส ไม่ crash
- เวลาประมวลผล PDF ใหญ่สุดในชุด < 30 วินาทีบนเครื่อง · ขนาดผล JSON < 1 MB

Human steps
- none

Stop conditions
- ความมั่นใจของ NB บนเอกสารต่างชนิดต่ำเกือบทั้งหมดจนป้ายไม่มีประโยชน์ → รายงานพร้อมตัวเลข เสนอทางเลือก (เช่น แสดงแค่ส่วน/ตัวเลข/คำแนะนำ)

Out of scope
- เขียนสรุปใหม่ของเอกสารทั่วไป (ตกลงว่าไม่ทำ), ชนิดเฉพาะของรอบ 1 (แผน 11)

## Phase 10.4: UI `/demo` v2: 3 ระดับ + ตัวเดินขั้นตอนแบบมีอนิเมชัน   [M]   [เจ้าของ: ผู้ช่วย; ผู้ใช้รีวิว]

Goal: ผู้ใช้อัปโหลด PDF แล้วเห็นขั้นตอนทีละขั้น (กดถัดไป/ย้อนกลับ) จนถึงผลลัพธ์ที่ตรงกับชนิดเอกสาร

Inputs
- 10.2-10.3, คอมโพเนนต์ v2 (7.2)

Tasks
1. `app/demo/_components/`: ตัวเดินขั้นตอน (`'use client'` ใบเดียว) แสดงขั้นตาม `trace.steps` ที่ได้ (ไม่ hard-code ลำดับต่อชนิด), ปุ่มถัดไป/ย้อนกลับ/ข้ามไปผล, คีย์บอร์ด (ลูกศรซ้าย/ขวา), `aria-live` บอกขั้นปัจจุบัน
2. ภาพต่อขั้น: ข้อความก่อน/หลังทำความสะอาด, ส่วนและหน่วย, ชิปโทเคน, ชิปที่ถูกคัด (ขีดฆ่า+จาง พร้อมเหตุผล), แท่งคะแนน NB + คำเด่น, ชิปเข้าภาค, ข้อเท็จจริงเข้าช่องเทมเพลต, รายการ F1-F5 พร้อมผ่าน/ไม่ผ่าน
3. ผลลัพธ์ตาม `kind`: `issue` ใช้ `issue-summary` เดิม; `generic` ใช้มุมมองใหม่ (ป้าย + ความมั่นใจ + "ไม่แน่ใจ", คำเตือน not_tmd_like); ชนิดรอบ 1 ใช้คอมโพเนนต์จากแผน 11 เมื่อพร้อม (ระหว่างนั้นแสดงแบบ generic)
4. `lib/contract/summarize.ts` + `lib/upload.ts` รองรับสัญญา v2 + ข้อความ error ภาษาไทยเดิม
5. `tests/e2e/demo.spec.ts`: mock คำตอบ 3 ระดับ, เดินครบทุกขั้นด้วยปุ่มและคีย์บอร์ด, reduced-motion, ภาพหน้าจอทุกขั้นที่ 375/1280 · `docs/spec/ui-spec.md` หัวข้อ `/demo`

Checks
- `npm run typecheck`, `lint`, `test`, `build`, `e2e` ผ่าน · grep กฎดีไซน์ 7.2 ผ่าน
- หลังผู้ใช้ push: อัปโหลด PDF จริง 3 แบบบนเว็บจริง (รายวัน, generic, ภาพล้วน) ได้ผลตามระดับ · `npm run smoke` ผ่าน (เพิ่มเทสต์ trace)

Human steps
- ผู้ใช้สั่ง push/deploy และลองอัปโหลดเอง แล้วเซ็นปิด

Out of scope
- ช่องพิมพ์ประโยคเอง, ชนิดเอกสารรอบ 1/2 เต็มรูปแบบ
