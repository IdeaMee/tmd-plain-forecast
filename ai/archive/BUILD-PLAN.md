## 0. หลักการกันหลอน / กันทำไม่ครบ

1. **แผนเป็นไฟล์ ไม่ใช่ความจำของแชท** ทุก session เริ่มด้วยการอ่าน BUILD-PLAN.md (หัวข้อ 0, 4 และ phase ของตัวเอง) + STATE.md + decision log ใน PLAN.md
2. **1 session = 1 phase** ทำเฉพาะไฟล์ที่ phase กำหนด ไม่เพิ่มฟีเจอร์นอกแผน
3. **ไม่มีคำว่า "เสร็จ" ถ้าไม่มีผลคำสั่งจริง** ทุกเกณฑ์ผ่านต้องเป็นคำสั่งที่รันได้ (ผลแปะใน STATE.md) ไม่ใช่คำบรรยาย
4. **สัญญาที่ตรึงไว้ก่อนเขียนโค้ด** (หัวข้อ 4: ชุดป้าย รูปแบบอินพุต/เอาต์พุต ชื่อภาค) เปลี่ยนได้ทางเดียวคือแก้ที่ไฟล์นี้ + บันทึก decision log แล้วค่อยแก้โค้ด
5. **ตรวจโดยคนละ session / ถ้าเป็นไปได้คนละโมเดลกับผู้เขียน** (หัวข้อ 7) เพราะผู้เขียนมักไม่เห็นข้อผิดของตัวเอง
6. **ข้อมูลจริงเท่านั้น** ตัวเลข ชื่อจังหวัด ประโยคแนะนำ ต้องมาจากข้อความต้นฉบับ ห้ามแต่ง ตัวอย่างทดสอบทั้งหมดมาจากไฟล์จริงใน `data/raw/`
7. **หยุดแล้วกลับมาถามที่แชทวางแผน** ถ้า phase เดียวกันแก้ไม่ผ่านเกิน 2 รอบ หรือพบว่าสัญญาข้อมูลผิด
8. **ห้ามใช้ git** ทุก session จนกว่าผู้ใช้สั่งในข้อความนั้นๆ (กฎของโปรเจกต์) ช่วง commit เพื่อส่งงานอยู่ที่ P7
9. **ห้ามใช้สคริปต์ดึงเว็บ TMD** ยกเว้นเรียก API ทางการตามที่ P1 ระบุ (นโยบาย TMD ข้อ 3.3) ส่วน PDF/HTML ผู้ใช้โหลดและคัดลอกเอง

## 4. สัญญาที่ตรึงไว้ (แก้ได้ที่นี่เท่านั้น)

### 4.1 ภาค 7 ภาค (ชื่อไทย <-> คีย์ใน API `TMDForecastDaily`)
เหนือ `north` · ตะวันออกเฉียงเหนือ `northeast` · กลาง `central` · ตะวันออก (รวมชายฝั่ง) `east` · ใต้ฝั่งตะวันออก (อ่าวไทย) `south_east_coast` · ใต้ฝั่งตะวันตก (อันดามัน) `south_west_coast` · กรุงเทพมหานครและปริมณฑล `bangkok_vicinity`
(ตรวจแล้วว่า API คืนฟิลด์เหล่านี้แยกภาคสะอาด พร้อม `general_climate` (ภาพรวมประเทศ), `description`, `pdf_url`, `contentdate`)

### 4.2 อินพุตของแอป
- ประเภทเอกสาร: `daily` หรือ `sevenday` (ผู้ใช้เลือก หรือแอปเดาจากหัวข้อ "พยากรณ์อากาศ 24 ชั่วโมงข้างหน้า" / "คาดหมายลักษณะอากาศ")
- ข้อความที่ผู้ใช้วาง (ไม่เกิน ~20,000 อักษร) + ภาค 1 จาก 7
- ข้อความจากหน้าเว็บ HTML ของ TMD (แนะนำ) หรือจาก PDF (ต้องทนต่อช่องว่างแทรกกลางคำและบล็อกภาคที่ถูกรวมกัน; ดู P2)

### 4.3 ชุดป้ายประโยค/อนุประโยค (draft v1 ต้องยืนยันใน P3)
| ป้าย | ความหมาย | ตัวอย่างจริง |
|---|---|---|
| `weather` | สภาพอากาศ/ตัวเลข ฝน อุณหภูมิ ลม คลื่น หมอก | "มีฝนฟ้าคะนองร้อยละ 30 ของพื้นที่ ส่วนมากบริเวณจังหวัดอุทัยธานี…" · "อุณหภูมิต่ำสุด 21-25 องศาเซลเซียส" |
| `advice` | ข้อแนะนำ/คำเตือนให้คนทำหรือระวัง | "ขอให้ประชาชนในภาคใต้ระวังอันตรายจากฝนตกหนักและฝนที่ตกสะสม ซึ่งอาจทำให้เกิดน้ำท่วมฉับพลัน…" |
| `cause` | สาเหตุเชิงกลไกอากาศ | "ทั้งนี้เนื่องจากบริเวณความกดอากาศสูงหรือมวลอากาศเย็น… มีกำลังอ่อนลง" · "ส่วนมรสุมตะวันออกเฉียงเหนือกำลังปานกลางพัดปกคลุม…" |
| `other` | หัวเรื่อง ผู้ลงนาม เบอร์โทร หมายเหตุเกณฑ์ ตัวเชื่อม | "สอบถามสภาพอากาศ โทร. 1182" |
ปัญหาที่ต้องตัดสินในการเขียนคู่มือป้าย (P3): ประโยคเดียวที่มีหลายหน้าที่ ("ภาคใต้มีฝนตกหนัก เนื่องจากมรสุม…") ต้องกำหนดว่าตัดที่ตัวเชื่อม "เนื่องจาก / ทั้งนี้เนื่องจาก / ประกอบกับ / ในขณะที่ / ส่วน" แล้วป้ายรายอนุประโยค

### 4.4 ผลลัพธ์ของแอป
- `daily` -> "ภาค X (24 ชั่วโมงข้างหน้า):" + ประโยคสั้น 2-4 ประโยค (สภาพ ตัวเลขพร้อมความหมาย) + ข้อแนะนำที่เกี่ยวกับภาคนั้นจากต้นฉบับ (คัดมาตรง)
- `sevenday` -> หัวข้อ "ภาค X" + รายการตามช่วงวัน ("14-16 พ.ย.: …") + ข้อควรระวังที่เกี่ยวกับภาคนั้น
- ท้ายผลลัพธ์ทุกครั้ง: ข้อความ "ตัวช่วยสรุป ไม่ใช่ประกาศทางการ ที่มา: กรมอุตุนิยมวิทยา (tmd.go.th)" และลิงก์ต้นทาง
- **กฎความถูกต้อง (ตรวจอัตโนมัติ ดู 7.3):** ตัวเลข/ช่วงตัวเลข/ชื่อจังหวัดทุกค่าต้องอยู่ในต้นฉบับของภาคนั้น; ประโยคแนะนำต้องคัดมาตรง; ห้ามเปลี่ยน "ร้อยละ N ของพื้นที่" เป็น "โอกาส N%"; ห้ามแต่งคำแนะนำ; ใช้เกณฑ์ของ TMD เท่านั้นเมื่ออธิบายระดับ (ฝน/อากาศหนาว)
- **กฎเลือกข้อแนะนำจากภาพรวมประเทศ:** ประโยคแนะนำที่พูดถึงภาค/จังหวัดของภาคที่เลือกใส่ในผลลัพธ์; ที่ไม่พูดถึงภาคใดเลย ("ติดตามประกาศจากกรมอุตุนิยมวิทยา") ใส่เป็นบรรทัดทั่วไป; ที่พูดถึงภาคอื่นเท่านั้นตัดทิ้ง (รายละเอียดตัดสินใน P5)

| คลังศัพท์อธิบาย | หน้า `/info/*` ของ TMD (มีคำนิยามอยู่แล้ว ดู `tmd-digest/C-html-pages.md` หัวข้อ 4.4) | ≤30 คำที่ปรากฏในประโยค `weather`/`advice` (เช่น น้ำป่าไหลหลาก ฝนสะสม ฝนฟ้าคะนอง ลมกระโชกแรง) พร้อม URL ต้นทาง | ผู้ใช้ตรวจ ตัวเอเจนต์ร่าง |

**ปริมาณป้าย:** 300-500 หน่วย (ยังไม่ได้นับว่าแต่ละฉบับมีกี่หน่วย รู้ตอน P2) ถ้าจากข้อมูลเริ่มต้นได้ไม่ถึง ให้เก็บฉบับเพิ่ม

**ข้อควรระวังที่ทำให้ผลลัพธ์ "สวยเกินจริง" (ต้องกันใน P3-P4):**
- ห้ามสร้างป้ายด้วยกฎชุดเดียวกับ baseline (ไม่งั้น baseline จะถูก 100% โดยกำเนิด) ป้ายสุดท้ายมาจากคน ส่วนการ "เสนอป้าย" ล่วงหน้าโดยโมเดลภาษาทำได้ แต่คนต้องตรวจทุกแถวและบันทึกว่าแก้กี่แถว
- ต้องแบ่ง train/dev/test **ตามวัน** (ไม่สุ่มรายประโยค) แล้ว freeze ชุดทดสอบก่อนเขียน baseline และไม่ดูผลชุดทดสอบจนกว่าจะปรับโมเดลเสร็จ
- ตรวจความสอดคล้องของป้าย: ผู้ตรวจคนที่สองติดป้ายซ้ำ 10% ของแถว เก็บอัตราตรงกัน

## 6. Phase การเจน (9 phase, แต่ละ phase = session สร้าง + session ตรวจ)

ผู้ใช้ไม่ต้องห่วงเรื่องเวลา จึงไม่ใส่กำหนดวัน; ขนาดเป็นเพียงความหนักโดยประมาณ (S/M/L)

| Phase | ชื่อ | ใครลงมือ | ขนาด |
|---|---|---|---|
| P0 | ฐานโครง + **deployment spike** + สัญญา | agent + ผู้ใช้ (บัญชี Vercel) | S-M |
| P1 | เก็บข้อมูลดิบ | agent (สคริปต์ API) + **ผู้ใช้ (ข้อมูล 7 วัน)** | S |
| P2 | โมดูลเตรียมข้อความ | agent | M |
| P3 | ติดป้ายข้อมูล | agent เสนอป้าย + **ผู้ใช้/ทีมตรวจทุกแถว** | M (งานคน) |
| P4 | โมเดล + วัดผล | agent | M |
| P5 | ดึงค่า + เขียนประโยค | agent | L |
| P6 | แอปเว็บ (API + หน้าเว็บ) | agent | M |
| P7 | รวมระบบ ตรวจรอบสุดท้าย deploy README | agent + ผู้ใช้ (deploy/git) | M |
| P8 | เอกสารส่งงาน (ไม่ใช่โค้ด) | agent + ผู้ใช้ | S |

### P0 ฐานโครง + deployment spike (ถอดความเสี่ยงอันดับ 1 ก่อน)
- **เป้าหมาย:** รู้แน่ว่า Python + pythainlp รันบน Vercel Hobby ได้หรือไม่ ก่อนลงแรงที่เหลือ
- **งาน:** สร้างโครงโฟลเดอร์หัวข้อ 3 (เปล่าๆ + `requirements.txt`), เขียน `api/health.py` ที่ตัดคำตัวอย่างด้วย newmm แล้วตอบ JSON, `vercel.json`, หน้า `public/index.html` เปล่า, README ฉบับร่าง, ยืนยันตัวเลข limits ที่หน้า Vercel docs ปัจจุบัน และเวอร์ชัน Python ที่รองรับ แล้วบันทึกใน STATE.md
- **ผู้ใช้ทำ:** ติดตั้ง Vercel CLI (`npm i -g vercel`) ล็อกอินบัญชีของตัวเอง deploy `tmd-plain-forecast/` (agent ไม่ล็อกอินแทน) และส่ง URL
- **เกณฑ์ผ่าน:** `GET <url>/api/health` ตอบ 200 และตัดคำ "ฝนฟ้าคะนองร้อยละ 30 ของพื้นที่" ได้ ฝน|ฟ้าคะนอง|ร้อยละ|30|ของ|พื้นที่ (หรือใกล้เคียงที่บันทึกไว้) บน URL จริง; บันทึกเวลาตอบครั้งแรก (cold start) และขนาด bundle ใน STATE.md
- **ถ้าไม่ผ่าน:** ใช้ทางถอยหัวข้อ 2 แล้วบันทึกใน decision log ก่อนไป P1

### P1 เก็บข้อมูลดิบ
- **งาน (agent):** `scripts/fetch_daily.py` เรียก API ทางการ **ครั้งเดียวต่อรัน** (หน่วงเวลา, ส่ง User-Agent ที่ระบุชื่อโครงการ, ไม่ retry วนถี่) บันทึก JSON ดิบพร้อมเวลาดึงลง `data/raw/daily/` สร้าง `data/raw/MANIFEST.csv` (ไฟล์, ประเภท, วันที่ข้อมูล, แหล่ง, วิธีได้มา)
- **งาน (ผู้ใช้):** เก็บพยากรณ์ 7 วัน ≥15 ฉบับเป็น `.txt` (คัดลอกจากหน้าเว็บ) หรือ PDF ที่โหลดด้วยมือ ตั้งชื่อ `sevenday_YYYY-MM-DD.txt` และเก็บ **ฉบับรายวันคัดลอกจากหน้า HTML อีก ≥3 ฉบับ** (ไว้ทดสอบว่าข้อความที่คนวางจริงหน้าตาเป็นอย่างไร)
- **เกณฑ์ผ่าน:** `python -m unittest tests.test_p1` ตรวจ: JSON parse ได้, ≥20 ฉบับรายวันและมี 7 ฟิลด์ภาคครบทุกฉบับ, MANIFEST ตรงกับไฟล์จริง, ≥15 ฉบับ 7 วันไม่ว่าง, ไม่มีไฟล์ซ้ำ
- **ห้าม:** ดึงหน้า HTML/PDF ของ TMD ด้วยสคริปต์

### P2 โมดูลเตรียมข้อความ
- **งาน:** `src/tpf/prep.py` (normalize: ลบช่องว่างแทรกกลางคำจากการตัดบรรทัด, แก้ "ำ" ที่เพี้ยนที่ทราบ, เลขช่วง "-"/"–"), แยกบล็อกภาคจากข้อความที่วาง (ใช้ชื่อภาค 7 แบบ ทั้งชื่อเต็ม/ย่อ), แยกช่วงวันของ 7 วัน (วลี "ในช่วงวันที่ a - b", "ส่วนในช่วงวันที่", "หลังจากนั้น"), ตัดเป็นอนุประโยคตามตัวเชื่อมหัวข้อ 4.3, `src/tpf/tokenize.py` (newmm + ลบช่องว่าง) ออกเป็น `data/processed/units.jsonl` (id, doc_id, date, region, type, text, tokens)
- **เกณฑ์ผ่าน:** unittest ใช้ข้อความจริง: (ก) ฉบับ API รายวัน -> หน่วยต่อภาคตรงกับฟิลด์ API; (ข) ฉบับรายวันคัดลอกจาก HTML -> แยกได้ 7 บล็อกครบ; (ค) ฉบับ 7 วัน -> แยกช่วงวันได้ตรงกับที่ผู้ใช้ตรวจ 3 ฉบับ; (ง) ข้อความขยะ/ว่างไม่ crash; ตรวจมือ 30 หน่วยสุ่ม ผู้ใช้เซ็นว่าถูก
- **ผลลัพธ์ต้องรายงาน:** จำนวนหน่วยทั้งหมดและต่อฉบับ (ใช้ยืนยันว่าถึง 300-500 หรือไม่)

### P3 ติดป้าย (งานคนมากสุด)
- **งาน:** `scripts/export_for_labeling.py` ออก `data/labeled/to_label.csv` (id, text, บริบทประโยคก่อน/หลัง, ป้ายที่เสนอ, ว่าง: ป้ายสุดท้าย); เขียนคู่มือป้าย `data/labeled/GUIDELINE.md` (นิยาม + ตัวอย่าง + กรณีก้ำกึ่ง); ผู้ใช้/ทีมตรวจและกรอกทุกแถว; คนที่สองติดซ้ำ 10%; สร้าง `labeled_v1.csv` + `split.json` (train/dev/test ตามวัน)
- **เกณฑ์ผ่าน:** ทุกแถวมีป้ายจากชุด 4 ป้าย; อัตราตรงกันของผู้ตรวจ 2 คนรายงานแล้ว (ถ้าต่ำกว่า 0.8 ให้แก้คู่มือแล้วติดป้ายซ้ำส่วนที่ขัด); split: วันของ test ไม่ปนกับ train/dev; ทุกป้ายมีใน train; จำนวนหน่วยต่อป้ายรายงานแล้ว; **ผู้ใช้เซ็นปิดชุด v1**
- **หลังปิด:** ห้ามแก้ป้ายชุด test อีก

### P4 โมเดล + วัดผล
- **งาน:** `src/tpf/nb.py` (Naive Bayes ตามสไลด์ ML 08, m-estimate), `knn.py` (ตาม ML 04), `baseline.py` (กฎ keyword เขียน **ก่อน**เปิดดูผล test + majority class), `features.py` (bag of words; TF-IDF เป็นตัวเลือกตาม NLP 4-1 ซึ่งสไลด์สูตร tf ขัดกันเอง ต้องเลือกแบบเดียวและบันทึก), `scripts/train_eval.py` -> `model/model.json`, `reports/metrics.md` (accuracy ของ 4 วิธี บน dev และ test, confusion matrix, ตัวอย่างผิด 3-5 ประโยคพร้อมวิเคราะห์)
- **เกณฑ์ผ่าน:** (ก) unittest เทียบ NB กับตัวอย่างคำนวณมือที่จดไว้ใน `notes/ML/08-bayesian-learning.md` ได้ค่าตรงกัน; (ข) รันซ้ำได้ผลเดิม (seed/ไม่มีสุ่มที่ไม่บันทึก); (ค) ใช้ test เพียงครั้งเดียวหลังตรึงตัวเลือกบน dev, บันทึกไว้ใน metrics.md; (ง) `model.json` โหลดได้และจัดประเภทข้อความตัวอย่างได้
- **ไม่ทำ:** P/R/F1 แยก, ROUGE/BLEU (ตัดสินแล้ว)
- **ข้อสังเกตตามจริง:** ถ้ากฎ keyword เท่าหรือดีกว่า Naive Bayes ให้รายงานตามจริง

### P5 ดึงค่า + เขียนประโยค (L)
- **งาน:** `extract.py` (regex ดึง: ช่วงอุณหภูมิต่ำสุด/สูงสุด, "ร้อยละ N ของพื้นที่", ชื่อจังหวัด, ความสูงคลื่น, ลม, ช่วงวัน), `glossary.py` + `glossary.json` (≤30 คำ ต้นทางทุกคำมี URL ของ TMD), `generate.py` (แม่แบบ + เกณฑ์ฝน/อากาศหนาวของ TMD), `pipeline.py` (prep -> NB -> เลือกบล็อกภาค -> extract -> generate; ใช้ชุดป้ายตัดสินว่าประโยคไหนเข้า/ออก), กฎเลือกข้อแนะนำตามหัวข้อ 4.4
- **เกณฑ์ผ่าน (อัตโนมัติ):** `tests/test_fidelity.py` กับเอกสารจริงทุกฉบับใน `data/raw/` และทุก 7 ภาค: F1 ตัวเลขทุกค่าในผลลัพธ์อยู่ในบล็อกภาคนั้นของต้นฉบับ; F2 ชื่อจังหวัดทุกชื่อมาจากต้นฉบับ; F3 ประโยคแนะนำทุกประโยคเป็นสตริงย่อยของต้นฉบับ (หลังจัดช่องว่าง); F4 ไม่มีรูปแบบ "โอกาส…%/ความน่าจะเป็น"; F5 ผลลัพธ์ภาค R ไม่มีตัวเลขที่พบเฉพาะบล็อกภาคอื่น; F6 รันซ้ำได้ผลเดิม; F7 ข้อความว่าง/ขยะ -> ข้อความผิดพลาดที่เป็นมิตร ไม่ crash; golden files 6 ฉบับ x 7 ภาค ใน `tests/golden/` ผู้ใช้อ่านตรวจ ≥10 ไฟล์
- **ข้อควรระวัง:** อย่าให้ P5 เพิ่มการอธิบายเอง (เช่น คำแนะนำ "พกร่ม") เกินคลังและเกณฑ์ของ TMD

### P6 แอปเว็บ
- **งาน:** `api/summarize.py` (รับ JSON `{type, text, region}` ตอบ `{summary_lines, advice, warnings, source}` หรือ error ที่ชัดเจน), `public/` (ช่องวาง, ตัวเลือกภาค 7 แบบ, ปุ่มตัวอย่าง 2-3 ฉบับ, ผลลัพธ์, ข้อความสงวนสิทธิ์+เครดิต TMD, อ่านง่ายบนมือถือ, สถานะกำลังโหลด/ผิดพลาด), จำกัดความยาวอินพุต
- **เกณฑ์ผ่าน:** รันบนเครื่อง (`vercel dev` หรือเซิร์ฟเวอร์ที่กำหนด) แล้วชุดทดสอบ end-to-end 15 กรณี (7 ภาค x 2 ประเภทเลือกบางส่วน + ข้อความขยะ + ว่าง + ยาวเกิน + ภาษาอังกฤษ + วางทั้งฉบับจาก PDF) ผ่านด้วยสคริปต์ยิง API; ตรวจ F1-F7 ผ่านทาง API ด้วย; ผู้ใช้ลองใช้เองบนมือถือ 1 ครั้ง

### P7 รวมระบบ ตรวจรอบสุดท้าย deploy
- **งาน:** deploy (ผู้ใช้), ชุดทดสอบ 15 กรณีรันบน URL จริง, ล่าบั๊ก (เกณฑ์หัก 0.5/จุด) ด้วย session ตรวจอิสระ, เขียน `README.md` ตามเกณฑ์ (Idea / วิธีใช้-รัน-ปรับแต่ง / ข้อมูล+ผลลัพธ์ / สมาชิก+บทบาท), เตรียมขั้นตอน git: **ผู้ใช้สั่ง** commit/push เอง (ทีมต้องมี commit ที่มีข้อความ)
- **เกณฑ์ผ่าน:** URL จริงผ่านชุดทดสอบ; README ครบ 4 หัวข้อ; ไม่มี secret/ไฟล์ใหญ่เกินจำเป็นใน repo; รายการข้อมูลดิบใน repo ตรงกับการตัดสินใจเรื่องลิขสิทธิ์/ai-train (ข้อ 11)

### P8 เอกสารส่งงาน
- **งาน:** โครงสไลด์ (Pain point+Idea / Solution+Product / Live demo), สคริปต์วิดีโอสาธิต, เตรียมคำถาม Q&A (เช่น ทำไม NB, ทำไมไม่ Transformer, "ฝนร้อยละ 30" ต่างจากโอกาสฝนอย่างไร, ข้อจำกัด), แผ่น results จาก `reports/metrics.md`
- **เกณฑ์ผ่าน:** ตัวเลขในสไลด์ตรงกับ `metrics.md` ทุกค่า (ตรวจโดย session แยก)

## 7. โปรโตคอลการตรวจ

### 7.1 ลำดับต่อ phase
1. **Session สร้าง** (ตามแม่แบบ 9.1) ทำ phase จนเกณฑ์ผ่านทุกข้อ แปะผลคำสั่งจริง อัปเดต STATE.md
2. **Session ตรวจ** (ตามแม่แบบ 9.2) **ใหม่ ไม่ใช่ผู้เขียน** อ่านเฉพาะแผน + ไฟล์ที่เปลี่ยน + ผลทดสอบ รันคำสั่งเกณฑ์ผ่านซ้ำเอง รายงานผ่าน/ไม่ผ่าน/ไม่แน่ใจพร้อมหลักฐาน ห้ามแก้โค้ด
3. ถ้าไม่ผ่าน: session สร้างแก้ตามรายการ ตรวจใหม่ (สูงสุด 2 รอบ แล้วหยุดกลับมาแชทวางแผน)
4. **ผู้ใช้เซ็นปิด phase** ใน STATE.md (ข้อความสั้นๆ) จึงเริ่ม phase ต่อไป

### 7.2 สิ่งที่ผู้ตรวจต้องทำเสมอ
- รันเกณฑ์ผ่านเองทุกข้อ ไม่เชื่อรายงานของผู้เขียน
- สุ่มเปิดข้อมูลจริง 5 รายการเทียบผลลัพธ์ด้วยตา
- หาสิ่งที่ผู้เขียน "ข้าม" หรือ "เดา" (ค้นคำว่า TODO, ตัวเลขที่ไม่มีที่มา, ข้อมูลที่ไม่อยู่ใน data/raw)
- ตรวจว่าไม่มีการเปลี่ยนสัญญาหัวข้อ 4 โดยไม่บันทึก decision log

### 7.3 การตรวจกันหลอนของผลลัพธ์ (F1-F7 ใน P5)
เป็นชุด unittest รันทุกครั้งที่แก้ pipeline/generate: ตัวเลขทุกค่าและชื่อจังหวัดต้องมาจากต้นฉบับของภาคนั้น, ประโยคแนะนำต้องคัดมาตรง, ห้ามรูปแบบ "โอกาส…%", ไม่มีตัวเลขของภาคอื่นปน, ผลซ้ำได้, อินพุตขยะไม่ crash

### 7.4 การตรวจผลลัพธ์ภาษา (คน)
ผู้ใช้/ทีมอ่าน golden files ว่าภาษาง่ายและไม่ผิดความหมาย (ที่ test อัตโนมัติจับไม่ได้) ใน P5 และ P7

## 8. STATE.md (ไฟล์ติดตามความคืบหน้า)
สร้างแล้วที่ [STATE.md](STATE.md) แต่ละ session ต้องอัปเดต: phase ปัจจุบัน, สิ่งที่ทำ, ผลคำสั่งจริง (วางตรงๆ), สิ่งที่ข้าม/ไม่แน่ใจ, สัญญาที่เปลี่ยน (ถ้ามี), ผู้ใช้เซ็นหรือยัง

## 10. โมเดลสำหรับสั่งเจน

- **ผมไม่มีข้อมูลเปรียบเทียบความสามารถหรือค่าใช้จ่ายระหว่าง Fable 5.2 กับ Opus 5.5 ในบริบทของคุณ** จึงไม่ขอตัดสินว่ารุ่นไหนเก่งกว่า สิ่งที่ผมรู้คือรุ่นที่มีอยู่ตอนนี้คือ Fable 5.2 (`claude-fable-5-2`), Opus 5.5, Sonnet 5.5, Haiku 5.5
- **คำแนะนำเชิงกระบวนการ:** (1) ใช้รุ่นที่แรงที่สุดที่แพ็กเกจของคุณให้ใช้ต่อเนื่องได้เป็นผู้สร้างใน P0, P4, P5, P6 ซึ่งต้องออกแบบและเขียนหลายไฟล์ (2) **ใช้อีกรุ่นเป็นผู้ตรวจ** (ถ้าสร้างด้วย Fable ให้ตรวจด้วย Opus และกลับกัน) เพื่อลดจุดบอดที่รุ่นเดียวกันมีร่วมกัน [inferred ไม่ได้ทดสอบ] (3) phase ที่เป็นงานกลไก (P1, P8) ใช้รุ่นเบาลงได้ถ้าต้องประหยัด
- ผลจริงของโปรเจกต์ขึ้นกับประตูตรวจ (หัวข้อ 7) มากกว่าการเลือกรุ่น จึงควรลงทุนกับเกณฑ์ผ่านที่รันได้จริง

## 11. สิ่งที่ผู้ใช้ต้องตัดสินใจ/เตรียมก่อนเริ่ม P0

1. **ยืนยันชุดเครื่องมือ:** Python + pythainlp + ฟังก์ชัน Python บน Vercel + หน้าเว็บ HTML/JS ล้วน (หรืออยากได้ Next.js แทน)
2. **มีบัญชี Vercel และ GitHub ของทีมหรือยัง** (P0 และ P7 ต้องใช้; agent ไม่ล็อกอินแทน)
3. **ใครติดป้ายข้อมูลใน P3** (ต้องมีผู้ตรวจอย่างน้อย 2 คน) และขนาด/บทบาททีม
4. **นโยบายข้อมูลใน repo:** จะใส่ข้อความ TMD (JSON/ข้อความ 7 วัน/ชุดป้าย) ลง repo สาธารณะหรือไม่ (หน้าลิขสิทธิ์ให้ใช้แบบไม่แสวงหากำไรโดยให้เครดิต แต่ `robots.txt` มี `ai-train=no`) และข้อมูลที่ดึงไว้ด้วยสคริปต์รอบสำรวจ (`data-samples/`, `tmd-digest/`) จะเก็บไว้ภายในหรือตัดออก
5. **ข้อมูล 7 วัน:** รับงานเก็บ ≥15 ฉบับเองได้หรือไม่ (P1)
6. **ชื่อแอปภาษาไทย/อังกฤษ** (ใช้ชื่อชั่วคราว `tmd-plain-forecast`)
7. **วันส่งจริง** (ยังไม่ทราบ ผู้ใช้บอกว่าไม่ต้องห่วง)
